# Аудит проекта и план миграции

Документ подготовлен по требованию раздела 0 мастер-техзадания: сначала аудит,
потом изменения. Здесь — фактическое состояние кода, расхождения с ТЗ и порядок работ.

Дата аудита: 2026-08-30. Аудируемый код: `~/kitchen-ai/frontend` (+ обёртка `~/kitchen-ai/mobile`).

---

## 1. Что реально есть

**Стек.** React 19, TypeScript (strict), Vite 8, Tailwind 4, react-router 7.
Бэкенда нет вообще — это чистое клиентское приложение.

| Область | Состояние |
| --- | --- |
| Интерфейс | Полный сценарий: главная → камера → подтверждение фото → параметры → генерация → результаты → чертежи → проекты → профиль |
| Работа с фото | Проверка типа и размера, учёт EXIF, сжатие до 1920 px, подготовка к отправке |
| Локальный renderer | `src/render` — трассировщик лучей: сцена из параметров, процедурные материалы, площадные источники света, мягкие тени, отражения, шумоподавление, проявка кадра. Считает в Web Worker |
| Анализ помещения | `src/analysis` — линии пола/столешницы/потолка, окна, свет, цвета, решение камеры по двум линиям, проверка пригодности снимка |
| Вписывание в фото | `src/render/pipeline.ts` — рендер только мебели с альфой, тень на реальный пол, подгонка экспозиции, заделка просветов |
| Чертежи | `src/drawings` — раскладка на модули, развёртка, план, схема столешниц с вырезами, спецификация, ведомость крепежа |
| Детерминированные расчёты | `src/drawings/hardware.ts` + 21 тест в `scripts/test-hardware.mjs` |
| Внешний ИИ | Абстракция провайдера: OpenAI Images, произвольный endpoint, Claude для разбора снимка |
| Хранение | `localStorage`: проекты (с уменьшённым фото в base64), настройки, ключи |
| Тесты | Только скрипты: анализ, композит, регрессия по 10 сценариям, чертежи, крепёж |
| Версионирование | **Отсутствует. Это не git-репозиторий.** |

## 2. Что соответствует техзаданию

- §29, §31, §32 — размеры модулей, фасадные зазоры, петли, направляющие и крепёж считаются
  детерминированным кодом с тестами. LLM к этим числам не допускается.
- §7, §223 — чертежи строятся из параметров проекта, а не из картинки.
- §34 — локальный renderer сохранён и используется как геометрический reference.
- §35 — своя diffusion-модель не обучается и не хостится.
- §39 — этапы генерации честные, фиктивных процентов нет; при неизвестном прогрессе
  показывается бесконечный индикатор.
- §42 — при работе с фото стены, пол, потолок, окна и перспектива не перерисовываются:
  комната остаётся фотографией, меняется только мебель.
- §79, §80 — есть mock-провайдер, тесты не тратят деньги.
- §95 — мобильный UX проверен на 375/768/1440, горизонтального overflow нет.
- §100 — нормативы эргономики в MVP не реализуются.

## 5. План миграции

Порядок выбран так, чтобы каждый этап давал работающий продукт, а не полуфабрикат.

**M0 — фиксация. ВЫПОЛНЕНО.**
`git init`, первый коммит, `.gitignore`.

**M1 — бэкенд и источник правды. ВЫПОЛНЕНО.**

- `shared/` — общий домен: схема `ProjectSpec` на Zod, статусы значений,
  проверка готовности. Один и тот же код у фронтенда и сервера.
- `backend/` — сервер на Node без веб-фреймворка, SQLite через встроенный
  `node:sqlite`. Компании, пользователи, сессии, производственные профили,
  проекты, ревизии, файлы, согласования, журнал действий.
- Ревизии неизменяемы: черновая правится на месте, согласованная блокируется,
  любое изменение спецификации после согласования создаёт новую ревизию.
- Файлы на диске, отдаются только своей компании. Публичных ссылок нет,
  тип проверяется по сигнатуре, имя из запроса в путь не попадает.
- Ключи провайдеров читаются только сервером; наружу отдаётся факт наличия
  ключа, а не он сам. Есть глобальный выключатель генерации.
- 19 интеграционных тестов: вход, ревизии, блокировка после согласования,
  изоляция компаний, приватность файлов, отсутствие утечки ключей.
- Фронтенд: вход и регистрация компании, проекты с сервера, спецификация
  уходит на сервер перед расчётом, BYOK помечен режимом разработчика.
- Фотография перестала быть обязательной (§12, §43).

Решение по СУБД: SQLite. MySQL на машине не установлен, а для одного цеха
файловая база с настоящими транзакциями достаточна и не требует обслуживания.
SQL написан переносимо: переезд на MySQL или PostgreSQL механический.

**M2 — каталог компании. ВЫПОЛНЕНО.**

- Схемы каталога в общем пакете: фасады, столешницы, корпусные материалы,
  фурнитура, техника, освещение. Атрибуты проверяются схемой своего типа —
  поля чужого типа не пройдут.
- CRUD каталога с изоляцией по компании. Запись не удаляется, а выключается:
  на неё могут ссылаться уже согласованные ревизии.
- Производственный профиль: толщины, зазор фасада, цоколь, глубины, кромка,
  марка фурнитуры. Есть значения по умолчанию, пока профиль не сохранён.
- Демо-каталог в сиде помечен DEMO: восемь записей, их видно, но за реальные
  они себя не выдают.
- Экран параметров строится из каталога компании: в спецификацию попадает
  идентификатор записи каталога, то есть конкретный артикул, а не абстрактный
  оттенок. Приложение больше не может предложить клиенту то, чего цех не делает.
- Раздел «Каталог» в приложении: просмотр по типам, добавление, выключение.
- 9 новых интеграционных тестов, всего 28.

**M3 — деньги и лимиты.**
Кредиты с журналом операций, серверные бюджеты, резервирование до вызова провайдера,
идемпотентность, kill switch, jobs со статусами и polling/SSE.

**M4 — ввод данных.**
Чат с парсером в структуру, карточка подтверждения, статусы значений
CONFIRMED/DERIVED/ESTIMATED/MISSING, разрешение конфликтов источников.
Фотография становится необязательной. Добавляются недостающие замеры:
ширина холодильника, размер варочной панели и мойки, положение воды и канализации.

**M5 — техпакет и смета.**
PDF из ProjectSpec без участия ИИ, с кириллицей и предупреждением о контрольном замере.
Смета со снимком цен на момент расчёта.

**M6 — расширение геометрии.**
Угловая планировка, обобщение модели до FurnitureObject/FurnitureModule,
затем шкаф и тумба поверх той же модели.

**M7 — роли и мультиарендность.**
OWNER/ESTIMATOR/CONSTRUCTOR, изоляция по компании, интеграционные тесты на изоляцию.
