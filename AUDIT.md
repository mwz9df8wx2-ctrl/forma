# Аудит проекта и план миграции

Документ подготовлен по требованию раздела 0 мастер-техзадания: сначала аудит,
потом изменения. Здесь — фактическое состояние кода, расхождения с ТЗ и порядок работ.

Дата аудита: 2026-08-30. Аудируемый код: `~/kitchen-ai/frontend` (+ обёртка `~/kitchen-ai/mobile`).

---

## 1. Что реально есть

**Стек.** React 19, TypeScript (strict), Vite 8, Tailwind 4, react-router 7.
Бэкенда нет вообще — это чистое клиентское приложение.

| Область | Состояние |
| --- | --- |
| Интерфейс | Полный сценарий: главная → камера → подтверждение фото → параметры → генерация → результаты → чертежи → проекты → профиль |
| Работа с фото | Проверка типа и размера, учёт EXIF, сжатие до 1920 px, подготовка к отправке |
| Локальный renderer | `src/render` — трассировщик лучей: сцена из параметров, процедурные материалы, площадные источники света, мягкие тени, отражения, шумоподавление, проявка кадра. Считает в Web Worker |
| Анализ помещения | `src/analysis` — линии пола/столешницы/потолка, окна, свет, цвета, решение камеры по двум линиям, проверка пригодности снимка |
| Вписывание в фото | `src/render/pipeline.ts` — рендер только мебели с альфой, тень на реальный пол, подгонка экспозиции, заделка просветов |
| Чертежи | `src/drawings` — раскладка на модули, развёртка, план, схема столешниц с вырезами, спецификация, ведомость крепежа |
| Детерминированные расчёты | `src/drawings/hardware.ts` + 21 тест в `scripts/test-hardware.mjs` |
| Внешний ИИ | Абстракция провайдера: OpenAI Images, произвольный endpoint, Claude для разбора снимка |
| Хранение | `localStorage`: проекты (с уменьшённым фото в base64), настройки, ключи |
| Тесты | Только скрипты: анализ, композит, регрессия по 10 сценариям, чертежи, крепёж |
| Версионирование | **Отсутствует. Это не git-репозиторий.** |

- §95 — мобильный UX проверен на 375/768/1440, горизонтального overflow нет.
- §100 — нормативы эргономики в MVP не реализуются.

## 4. Проверка запуска

Состояние на момент аудита (до миграции):

```
npm run typecheck   без ошибок
npm run build       проходит, основной бандл 123 КБ gzip
npm run lint        3 предупреждения (штатные шаблоны загрузки данных)
node scripts/test-hardware.mjs     21 проверка пройдена
node scripts/test-regression.mjs   10 сценариев пройдены
```

После M0–M7:

```
backend  npm test        71 интеграционный тест
backend  npm run typecheck   без ошибок
frontend npm test        21 + 124 проверки и 10 сценариев рендера
frontend npm run build   проходит, основной бандл ~170 КБ gzip
```

Сценарий проходится целиком: замеры → параметры → визуализация → чертежи →
техпакет со сметой.

## 5. План миграции

Порядок выбран так, чтобы каждый этап давал работающий продукт, а не полуфабрикат.

**M0 — фиксация. ВЫПОЛНЕНО.**
`git init`, первый коммит, `.gitignore`.

**M1 — бэкенд и источник правды. ВЫПОЛНЕНО.**

- `shared/` — общий домен: схема `ProjectSpec` на Zod, статусы значений,
  проверка готовности. Один и тот же код у фронтенда и сервера.
- `backend/` — сервер на Node без веб-фреймворка, SQLite через встроенный
  `node:sqlite`. Компании, пользователи, сессии, производственные профили,
  проекты, ревизии, файлы, согласования, журнал действий.
- Ревизии неизменяемы: черновая правится на месте, согласованная блокируется,
  любое изменение спецификации после согласования создаёт новую ревизию.
- Файлы на диске, отдаются только своей компании. Публичных ссылок нет,
  тип проверяется по сигнатуре, имя из запроса в путь не попадает.
- Ключи провайдеров читаются только сервером; наружу отдаётся факт наличия
  ключа, а не он сам. Есть глобальный выключатель генерации.
- 19 интеграционных тестов: вход, ревизии, блокировка после согласования,
  изоляция компаний, приватность файлов, отсутствие утечки ключей.
- Фронтенд: вход и регистрация компании, проекты с сервера, спецификация
  уходит на сервер перед расчётом, BYOK помечен режимом разработчика.
- Фотография перестала быть обязательной (§12, §43).

Решение по СУБД: SQLite. MySQL на машине не установлен, а для одного цеха
файловая база с настоящими транзакциями достаточна и не требует обслуживания.
SQL написан переносимо: переезд на MySQL или PostgreSQL механический.

**M2 — каталог компании. ВЫПОЛНЕНО.**

- Схемы каталога в общем пакете: фасады, столешницы, корпусные материалы,
  фурнитура, техника, освещение. Атрибуты проверяются схемой своего типа —
  поля чужого типа не пройдут.
- CRUD каталога с изоляцией по компании. Запись не удаляется, а выключается:
  на неё могут ссылаться уже согласованные ревизии.
- Производственный профиль: толщины, зазор фасада, цоколь, глубины, кромка,
  марка фурнитуры. Есть значения по умолчанию, пока профиль не сохранён.
- Демо-каталог в сиде помечен DEMO: восемь записей, их видно, но за реальные
  они себя не выдают.
- Экран параметров строится из каталога компании: в спецификацию попадает
  идентификатор записи каталога, то есть конкретный артикул, а не абстрактный
  оттенок. Приложение больше не может предложить клиенту то, чего цех не делает.
- Раздел «Каталог» в приложении: просмотр по типам, добавление, выключение.
- 9 новых интеграционных тестов, всего 28.

**M3 — деньги и лимиты. ВЫПОЛНЕНО.**

- Кошелёк кредитов и журнал операций. Баланс не меняется мимо журнала:
  сумма всех credit_delta компании равна её балансу, и это проверяется тестом.
- Порядок запуска жёсткий: проверка проекта и готовности спецификации →
  частота → одновременные задания → кредиты → бюджеты → резерв → создание
  задания. Резерв и создание задания идут в одной транзакции, поэтому
  списания без задания и задания без списания не бывает.
- Кредиты списываются до обращения к провайдеру. При сбое возвращаются
  отдельной строкой журнала — движение видно, а не выглядит как будто
  списания не было.
- Идемпотентность по заголовку `Idempotency-Key`: двойное нажатие и повтор
  запроса браузером отдают то же задание, а не второе платное.
- Жёсткие бюджеты на стороне сервера: месяц на пользователя, месяц на
  компанию, день и месяц на платформу, потолок вариантов за запуск,
  одновременные задания и частота запусков. Считаются в копейках по деньгам
  провайдера, а не по кредитам: кредиты можно подарить, счёт приходит настоящий.
- Очередь заданий со стадиями queued → preparing → generating → validating →
  saving → completed/failed. Прогресс приходит от сервера по стадии; полосы,
  которая ползёт при мёртвом задании, нет.
- Повтор внутри задания только для временных ошибок, не больше двух попыток,
  и он не резервирует кредиты заново.
- Общий выключатель `AI_GENERATION_ENABLED` останавливает новые запуски,
  не трогая проекты, расчёты и чертежи.
- Тестовый провайдер отдаёт настоящие байты PNG: тесты и разработка проходят
  тем же путём, что и бой, и не тратят денег.
- Подсказка к провайдеру собирается на сервере из ProjectSpec. Клиент
  присылает только пожелания до 400 символов: иначе любой, кто откроет
  консоль, оплатил бы из бюджета компании что угодно.
- Прерванные перезапуском задания закрываются при старте сервера с возвратом
  кредитов: доигрывать их нельзя, неизвестно, что успел сделать провайдер.
- В приложении: остаток кредитов в боковой панели и в профиле, история
  операций, стоимость запуска на кнопке, пустое состояние «AI-кредиты
  закончились. Проекты, расчёты и чертежи продолжают работать», сообщение
  о возврате при сбое.
- Настоящая генерация включается только когда сервер сообщает о подключённом
  провайдере. Без ключа изображение считается на устройстве: заглушка была бы
  хуже локального расчёта, и кредиты за неё брать не за что.
- 13 новых интеграционных тестов, всего 41.

**M4 — ввод данных. ВЫПОЛНЕНО.**

- Лист замеров выводится из спецификации: помещение, техника, вода и
  канализация. У каждого значения виден статус — замер, расчёт, предположение
  или пусто — и написано, зачем этот размер нужен.
- Разбор текста замера работает по правилам и без всякой модели: находит
  числа, понимает «см», «м» и «2,65 м», разделяет «холодильник 600, мойка 800»
  и отбрасывает опечатки на порядок вроде «холодильник 6000».
- Каждое предложение сопровождается фрагментом исходного текста. Замерщик
  сверяет число за секунду, а не верит разбору на слово.
- Разбор ничего не записывает. Значение попадает в спецификацию только через
  подтверждение и только тогда получает статус «замер».
- Конфликт с уже подтверждённым замером помечается отдельно и по умолчанию
  не отмечен: перезапись замера — решение человека, а не разбора.
- Подтверждение проходит через то же правило ревизий, что и ручной ввод:
  черновик правится на месте, согласованная ревизия порождает новую.
- Модель подключается поверх правил и стоит кредит по тому же порядку, что и
  генерация: проверка кредитов и бюджета до вызова, возврат при сбое. Если
  модель не участвовала, кредит не берётся. Ей запрещено выводить размер из
  других размеров и подставлять типовые значения — она только раскладывает
  по полям то, что человек написал.
- Диалог сохраняется: видно, кто что написал, что распознал разбор и что
  подтвердил человек.
- Над чертежами появляется предупреждение, если замер неполный: лист по
  предположениям выглядит так же убедительно, как по замеру, и именно поэтому
  по нему режут материал.
- Открытый проект переживает перезагрузку страницы — иначе замерщик на объекте
  начинал бы заново после каждого перехода по ссылке.
- 11 новых интеграционных тестов, всего 52.

**M5 — техпакет и смета. ВЫПОЛНЕНО.**

- Техпакет собирается из ProjectSpec и той же геометрии, что и чертежи:
  титул с параметрами, развёртка, план, столешница, спецификация модулей,
  ведомость крепежа и смета. Модель в этом не участвует.
- Предупреждение о контрольном замере печатается всегда, а не только при
  неполном замере: лист уходит в цех, и стены редко бывают ровными.
- PDF делает печать браузера. Он вкладывает шрифт сам, поэтому кириллица
  остаётся выделяемым текстом. Свой генератор PDF со сборкой подмножества
  шрифта дал бы то же самое, но с риском получить нечитаемый лист в цеху.
- Ведомость материалов считается из того же раскроя, что и чертежи:
  площадь фасадов, погонные метры столешницы, площадь корпусных деталей,
  крепёж по нормам. Количество на чертеже и в смете совпадает по построению.
- Цены подставляет сервер из каталога компании. Цена, пришедшая из браузера,
  игнорируется — это проверяется тестом.
- Смета сохраняется снимком: изменение цены в каталоге не трогает уже
  посчитанную смету. Тоже под тестом.
- Позиции без цены помечаются и не завышают сумму: видно, чего не хватает
  в каталоге, а не красивый неверный итог.
- Деньги переведены на целые копейки, включая цены каталога. REAL в деньгах
  убран: смета из сотни позиций расходилась бы с накладной на округлении.
- Появился лёгкий механизм миграций (`ensureColumn`): база, созданная до
  появления цен, дополняется на месте, а не падает на первом запросе.
- Открытый проект восстанавливается с сервера после перезагрузки страницы —
  прямая ссылка на техпакет или замеры больше не открывает пустой проект.
- 5 новых интеграционных тестов, всего 57.

**M6 — расширение геометрии. ВЫПОЛНЕНО.**

- Угловая планировка доведена до конца: боковой фронт есть и в чертежах,
  и в геометрии сцены. Картинка и чертёж показывают одну кухню — это
  проверяется тестом, а не глазами.
- Угол принадлежит основному фронту, боковой ряд начинается за глубиной
  столешницы. Иначе два корпуса встали бы в одно место, и цех получил бы
  лишний модуль, которому некуда встать.
- Угловой модуль помечен: 165° петли и десять дополнительных конфирматов
  считаются автоматически. Пенал в угловой кухне переезжает от боковой стены.
- Две развёртки вместо одной: по основной и по боковой стене. На одном листе
  их рисовать нельзя — модули отложены по разным осям.
- Столешница угловой кухни — две детали и стык под 90° со стяжками.
  Цельная Г-образная плита делается на заказ и стоит других денег.
- Модель обобщена: KitchenLayout и KitchenModule стали FurnitureLayout и
  FurnitureModule, у объекта появились категория и признак наличия столешницы.
- Шкаф и тумба собираются из тех же типов модулей: секции во всю высоту,
  полки, штанга, блок ящиков, антресоль. Чертежи, спецификация, крепёж и смета
  работают для них без единой отдельной ветки — второй набор правил рано или
  поздно разошёлся бы с первым прямо на раскрое.
- Внутренний блок ящиков не получает ни ножек, ни клипс цоколя: он опирается
  на чужие боковины. Для этого у модуля появился признак «внутренний».
- Лист «Схема столешниц» для шкафа не выпускается: пустой лист в цеху хуже
  отсутствующего.
- Визуализация корпусной мебели — шкаф, тумба, ТВ-зона, стенка в гостиную,
  прихожая, мебель для ванной, стеллаж — строится по модулям раскладки,
  а не пишется под каждую категорию заново.
  Картинка физически не может показать другое число дверец, чем спецификация:
  и то, и другое читается из одного списка модулей.
- Открытая секция стала производственным фактом: у неё нет дверцы, петель
  и ручки, и в спецификацию она уходит именно такой. Раньше картинка рисовала
  нишу, а спецификация считала для неё петли.
- У модуля появился явный признак ящика: ящику нужны направляющие, дверце —
  петли, и определять это по названию модуля было ненадёжно.
- Ширина секции стеллажа считается от допустимого пролёта полки, а не делится
  «на глаз»: ЛДСП 16 мм при пролёте больше 800 мм провисает за пару лет,
  и это претензия к цеху, а не к плите.
- У модуля появился признак «стоит на полу или висит на стене». Мебель ванной
  подвесная: под ней моют пол, поэтому у неё нет ни цоколя, ни ножек, и вся
  нагрузка идёт на навесы — крепёж считается именно так.
- Три варианта снимаются с трёх ракурсов — фронтально и в две четверти.
  Одна фронтальная картинка не отвечает на вопрос, как изделие встанет
  в комнату: по ней не видно ни глубины, ни торцов. Ракурс можно и задать
  вручную, тогда все варианты снимаются с него.
- Перед вписыванием новой мебели со снимка снимается прежняя. Новая кухня,
  положенная поверх старой, выдаёт себя по краям: торчат прежние фасады,
  ручки и техника. Нижний ряд снимается по геометрии — по его кромке разбор
  и нашёл линию столешницы, — верхний по цвету относительно стены, дыры
  закрашиваются протяжкой соседних пикселей по вертикали, чтобы сохранилась
  тень. Окна защищены отдельно. Если мебель не отделяется от стены, снимок
  остаётся как был, и это записано в журнал.
- Вписывание в фотографию оставлено только кухне. Разбор снимка построен на
  линиях пола и столешницы; шкаф по этим линиям — мебель, приклеенная к чужой
  геометрии, и приложение честно говорит об этом.
- 39 проверок раскладки (было 0), 21 проверка крепежа, 10 сценариев рендера.

**M7 — роли и мультиарендность. ВЫПОЛНЕНО.**

- Три роли: владелец, замерщик, конструктор. У каждой свой список прав,
  описанный в одном месте и общий для сервера и приложения.
- Права проверяются на сервере на каждом запросе. Скрытая кнопка — удобство,
  а не защита: запрос можно отправить и без неё.
- Замерщик читает каталог, но не меняет цены. Конструктор правит спецификацию,
  но не согласовывает ревизию и не тратит кредиты. Сообщение об отказе говорит,
  к кому идти за доступом, а не просто «нет прав».
- Сотрудники приглашаются по одноразовой ссылке. Пароль сотрудник задаёт сам:
  владелец не должен знать чужой пароль, а временный пароль в переписке живёт
  дольше, чем нужно. В базе хранится только отпечаток токена.
- Приглашение действует неделю, используется один раз и отзывается.
  Число сотрудников ограничено тарифом.
- В компании обязан остаться хотя бы один владелец, и себя нельзя отключить:
  иначе компания становится неуправляемой.
- Отключение сотрудника обрывает его сессии — по старому токену доработать
  смену не получится.
- Пока роль неизвестна, интерфейс ничего не прячет: при обрыве связи владелец
  не должен терять свои кнопки.
- 12 новых интеграционных тестов, всего 69.
